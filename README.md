# WON 해결패스 · 인터랙티브 프로토타입
## [데모 보러가기](https://nekerworld.github.io/WON-Solution-Pass/)

2026 우리은행 X SSAFY 아이디어 경진대회(WIN & WON) 본선 시연용 프로토타입입니다.

"이체가 안 돼요"라는 상황에서 출발해 **자동 진단 → 상태 기반 해결 경로 계산 → 단계별 안내 → 상태 재확인 → 원래 이체 복귀 → 거래 결과 검증**까지 한 흐름으로 보여 주는, 우리WON뱅킹 내장형 금융 업무 오류 해결 서비스입니다.

> **고지** — 이 프로토타입은 실제 은행 시스템과 연결되어 있지 않습니다. 모든 계좌·금액·고객 정보·거래는 브라우저 안에서만 동작하는 **가상 데이터**이며, 화면에 표시되는 한도·인증 규칙은 시연을 위해 정의한 **가상 정책(`DEMO-POLICY-2026.11`)** 입니다. 실제 우리은행의 정책이나 시스템을 나타내지 않습니다. 실제 OTP 번호, 비밀번호, 신분증 정보는 요구하지 않으며 외부 API·LLM을 호출하지 않습니다.

## 실행 방법

빌드, 설치, 서버가 필요 없습니다.

1. 저장소를 내려받습니다.
2. `index.html`을 Chrome 또는 Edge로 엽니다. 더블클릭해서 `file://`로 열어도 동작합니다.

| URL 옵션 | 동작 |
| --- | --- |
| `index.html` | 기본 실행. PC에서는 화면 왼쪽 절반에 스마트폰 프레임, 오른쪽 절반에 시연 제어 패널이 표시됩니다(너비 1400px 이상이면 패널이 조작 열과 관찰 열 2단으로 나뉩니다). |
| `index.html?selftest=1` | 로드 직후 자가 테스트를 자동 실행합니다. 결과는 시연 패널과 `window.__WSP_SELFTEST__`에 기록됩니다. |
| `index.html?demo=1` | 좁은 화면(900px 이하)에서도 시연 패널을 여는 `DEMO` 버튼을 표시합니다. |

- **Shift + D**: 시연 제어 패널 표시/숨김 (숨기면 폰 영역이 전체 너비를 사용합니다)
- 화면 너비가 520px 이하면 폰 프레임 없이 전체 화면 앱으로 표시됩니다(실제 모바일 기기용).
- 상태는 `sessionStorage`에 저장되므로 새로고침해도 유지됩니다. 처음 상태로 돌아가려면 패널의 **데모 초기화**를 누르세요.

### GitHub Pages 배포

`master`에 push하면 `.github/workflows/deploy-pages.yml`이 `index.html`, `css/`, `js/`만 모아 GitHub Pages에 배포합니다. 제안서 PDF와 README는 게시되지 않습니다.

- 최초 1회: 저장소 **Settings → Pages → Build and deployment → Source**를 **GitHub Actions**로 설정합니다.
- 수동 배포: **Actions → Deploy prototype to GitHub Pages → Run workflow**
- 배포 주소: `https://nekerworld.github.io/WON-Solution-Pass/`

## 기본 시연 순서 (Case A · 정상 복구)

초기 상태: 150만원 이체 요청, 1일 이체한도 100만원, 디지털 OTP 미등록, 고객확인 완료, 잔액 충분.

1. 홈에서 **이체**를 누릅니다. 받는 분 홍길동, 금액 1,500,000원이 미리 채워져 있습니다.
2. **이체하기**를 누르면 은행 사전 검사가 실패하고, 해결패스가 **자동으로** 진단 시트를 띄워 6개 항목을 조회합니다.
   진단이 끝나도 화면은 자동으로 넘어가지 않습니다. 결과를 확인한 뒤 **해결 계획 보기**를 눌러야 다음 화면으로 이동합니다(시트 바깥을 눌러 닫으면 현재 화면에 머물고, 홈의 해결패스에서 다시 볼 수 있습니다).
3. 해결 계획 화면이 나타납니다: *"150만원 이체를 진행하려면 다음 두 가지 설정이 필요합니다."*
   경로는 `디지털 OTP 등록 → 이체한도 변경 → 원래 이체로 돌아가기` 순서입니다.
4. **디지털 OTP 등록하러 가기** → **디지털 OTP 등록 진행** → **해결패스로 돌아가기**를 차례로 누릅니다.
   해결패스가 은행 상태를 다시 조회하고 남은 경로를 다시 계산합니다.
5. **이체한도 변경하러 가기** → 150만원 선택 → **변경 가능 여부 확인** → **이 한도로 변경** → **해결패스로 돌아가기**를 누릅니다.
6. "이체 사전 조건을 모두 확인했어요" 화면에서 **원래 이체로 돌아가기**를 누릅니다. 입력했던 이체 정보가 그대로 유지됩니다.
7. **이체하기** → 확인 모달에서 받는 분과 금액을 확인한 뒤 **보내기**를 누릅니다. 사용자가 직접 승인하기 전에는 거래가 실행되지 않습니다.
8. 가상 은행이 `SUCCESS`를 반환한 경우에만 **"이체 완료를 확인했어요"** 와 거래 확인번호가 표시됩니다.
9. 홈의 **질문하기**에서 "150만원을 보내려는데 왜 안 돼?" 같은 질문을 하면, 현재 은행 상태에 맞는 답변과 기능 바로가기 버튼이 표시됩니다.

## 예외 시나리오 (시연 패널 프리셋)

프리셋을 누르면 데모를 초기화한 뒤 해당 가상 상태를 설정합니다. 그다음 앱에서 이체를 시도하세요.

| 프리셋 | 상태 | 기대 동작 |
| --- | --- | --- |
| A 정상 복구 | 기본 상태 | OTP 등록 → 한도 변경 → 원래 이체 → 성공 확인 |
| B OTP만 | 한도 200만원, OTP 미등록 | OTP 등록만 안내 |
| C 한도만 | OTP 등록됨, 한도 100만원 | 한도 변경만 안내 |
| D 모두 충족 | OTP 등록됨, 한도 200만원 | 불필요한 절차 없이 바로 승인 확인 |
| E 계좌 제한 | 계좌 이용 제한 | 해제 방법을 만들어 내지 않고 공식 상담 안내 |
| F 은행 장애 | 은행 시스템 이용 불가 | 정상 진단을 가장하지 않고 오류·재확인 안내 |
| KYC 미완료 | 고객확인 미완료 | `고객확인 → OTP → 한도` 순서로 경로 계산 |
| 경로 없음 | 비대면 한도 변경 불가 | 허용된 경로가 없으면 상담 안내 (`NO_PATH`) |

- **Case G (결과 불명확)**: 패널의 *다음 거래 결과*에서 `PENDING` 또는 `UNKNOWN`을 고른 뒤 이체하면, 완료로 표시하지 않고 재이체를 막은 채 결과 조회를 안내합니다. 패널의 **은행 확정 SUCCESS / FAILED**로 은행 측 확정을 흉내 낸 뒤 앱에서 **결과 조회**를 누르면 결과가 반영됩니다.
- **Case H (모호한 질문)**: 채팅에서 "오늘 날씨 어때?"처럼 지원하지 않는 질문을 하면, 금융 정보를 지어내지 않고 질문 예시와 상담 안내를 보여 줍니다.
- **상태 조회 실패 주입** 스위치를 켜면 은행 상태 조회가 실패합니다. 이때 해결패스는 경로를 계산하지 않고 상담·재확인을 안내합니다.

  mockBank.js       비동기 가상 은행 API (조회·변경·사전 검사·이체 제출·결과 조회)

## 구조 요약

**중앙 상태 저장소** (`WSP.store`)
- 계좌, 고객, 이체 초안, 거래, 시뮬레이션, 시스템 상태를 한곳에서 관리합니다.
- 상태가 바뀔 때마다 `stateVersion`이 1씩 증가하고, 구독 중인 화면과 패널이 갱신됩니다.

**상태머신(FSM)**
- 상태: `IDLE`, `DIAGNOSING`, `PLAN_READY`, `WAITING_USER`, `RECHECKING`, `READY_TO_RETRY`, `VERIFYING`, `COMPLETED`, `ESCALATED`, `RESULT_UNCERTAIN`
- 상태 전이는 데이터 테이블로 정의되어 있으며, 테이블에 없는 전이는 거부됩니다.
- `PENDING` 결과일 때는 `VERIFYING`에 머무릅니다.
- `ESCALATED`: 앱 안에서 해결할 수 없어 상담·재확인으로 넘긴 상태입니다(차단 사유, 경로 없음, 이체 실패 확정). 출금이 불확실한 거래가 없으므로 다시 진단하거나 새 건으로 돌아갈 수 있습니다.
- `RESULT_UNCERTAIN`: 이체 결과가 `UNKNOWN`이라 출금 여부를 알 수 없는 상태입니다. 중복 출금을 막기 위해 재진단·새 건으로 가는 전이가 없고, 결과 조회(`RESULT_QUERY`)로만 빠져나갑니다.
- 결과 화면에서 **홈으로**(또는 뒤로)를 누르면 사건을 종료합니다: `COMPLETED`·`ESCALATED`는 `NEW_CASE`로 `IDLE`에 돌아가고, `VERIFYING`·`RESULT_UNCERTAIN`은 그대로 유지됩니다.

**Rule Engine**
- 차단 규칙: R06 은행 이용 불가, R05 계좌 제한, R07 잔액 부족
- 요구사항: R04 고객확인, R02 디지털 OTP, R01 이체한도
- 제약 조건: R03 한도 상향 전 OTP, R08 OTP 등록 전 고객확인
- 디지털 OTP는 가상 정책상 100만원을 넘는 이체에만 요구됩니다.

**경로 탐색 (상태 그래프 + 다익스트라)**
- 행동: `REGISTER_OTP`, `CHANGE_TRANSFER_LIMIT`, `COMPLETE_KYC`, `RETURN_TO_TRANSFER`, `ESCALATE_TO_SUPPORT`
- 각 행동의 사전 조건과 효과를 데이터로 정의합니다. 현재 은행 상태에서 출발해 적용 가능한 행동으로 도달하는 상태들을 노드로 펼쳐 상태 그래프를 만듭니다(깊이 최대 6).
- 간선 가중치는 가상 정책 `DEMO_POLICY.actionWeights`에서 가져옵니다: 고객확인 5, OTP 등록 3, 한도 변경 2, 이체 복귀 1. 사용자 부담과 인증 강도를 반영한 **시연용 가상 값**이며 실제 은행 기준이 아닙니다.
- 다익스트라(최소 힙)로 가중치 합이 가장 작은 경로를 고릅니다. 단계 수가 적어도 비용이 크면 선택하지 않습니다.
- 시연 패널에서 상태 그래프, 각 노드까지의 비용(`d=`), 선택된 경로를 시각화합니다.
- 차단 사유가 있거나 경로가 없으면 상담 절차로 넘깁니다.

**가상 은행 API**
- 모든 호출이 지연 시간이 있는 비동기 함수입니다.
- 실패 응답은 조회 실패(`QUERY_FAILURE`)와 업무 거절(`BUSINESS_REJECT`)로 구분됩니다.
- 이체는 `requestId`로 멱등성을 보장해 같은 요청이 중복 거래를 만들지 않습니다.
- 결과 조회 함수는 이체를 재전송하지 않습니다.

**화면 연결**
- 챗봇과 해결 계획의 바로가기는 허용목록에 있는 내부 화면 ID로만 이동합니다. 외부 URL은 만들지 않습니다.

**자연어 질문** (`RULE_BASED_SIMULATION`)
- 문장 정규화, 금액 추출(예: "150만원", "1,500,000원", "백오십만원"), 복합 의도 인식을 규칙으로 처리합니다.
- 사용자의 말이 은행 기록과 다르면 은행 기록을 기준으로 답합니다.

## 자가 테스트

패널의 **자가 테스트 → 실행** 또는 `?selftest=1`로 실행합니다. 실행 전의 상태를 저장해 두었다가 테스트가 끝나면 그대로 복원합니다.

**자동 테스트 범위**
- 명세 14장 필수 테스트 1~12번
- 정의되지 않은 FSM 전이 거부
- KYC 선행 순서
- 100만원 이하 이체에는 OTP를 요구하지 않음
- 경로 없음(`NO_PATH`)
- 해석 불가 질문
- 금액과 사용자 진술 추출
- 이체 결과 문의 의도
- 화면 연결 허용목록
- 정책상 한도 변경 거절

**브라우저에서 직접 확인한 항목 (13~15번)**
- 모바일 레이아웃
- PC 스마트폰 프레임 표시
- 콘솔 오류 없음
